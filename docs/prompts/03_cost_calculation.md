# Расчёт стоимости использования LLM

## Методология расчёта

Данный документ предоставляет детальные расчёты стоимости использования LLM для различных сценариев использования XX Auto Jobs Applier.

**Базовые предположения**:
1. Используется модель **gemini-2.0-flash** (оптимальное соотношение цена/качество)
2. Цены: $0.10 / 1M input токенов, $0.40 / 1M output токенов
3. Режим работы: Обычный (не MONKEY_MODE)
4. Фиксированное письмо: Не используется (генерация через LLM)

### Взвешенная средняя стоимость на вакансию

**Формула**:
```
Средняя стоимость = Σ (Вероятность × Стоимость сценария)
```

**Расчёт**:
```
= 0.45 × $0.00075   (минимум, отсев)
+ 0.35 × $0.00126   (без вопросов)
+ 0.15 × $0.00200   (с вопросами, среднее)
+ 0.05 × $0.00250   (много вопросов)

= $0.000338 + $0.000441 + $0.000300 + $0.000125
= $0.001204
```

**Средняя стоимость на одну проверенную вакансию**: **$0.00120**

**Стоимость на один УСПЕШНЫЙ отклик**:
```
Успешных откликов = ~50% от проверенных
Средняя стоимость успешного = $0.00120 / 0.50 = $0.00240
```

### Сценарий Б: 10,000 вакансий в день (обработка сервером)

**Контекст**:
- Сервер обрабатывает вакансии для всех пользователей
- Массовая проверка новых вакансий

**Предположения**:
- Проверка всех 10,000 вакансий
- Отсев ~45% по score < 60
- Успешная обработка ~5,500 вакансий

**LLM вызовы**:

| Действие | Количество | Стоимость за единицу | Итого |
|----------|-----------|---------------------|-------|
| Проверка всех вакансий | 10,000 | $0.00120 | $12.00 |

**Итого в день**: **$12.00**  
**Итого в месяц** (30 дней): **$360.00**  
**Итого в год** (365 дней): **$4,380.00**

**Оптимизации для снижения стоимости**:

#### 1. Кэширование суммаризации вакансий

**Проблема**: Одна и та же вакансия может быть проверена несколькими пользователями

**Решение**: Кэш суммаризации по `vacancy_id`

**Структура кэша**:
```yaml
vacancy_summaries:
  "12345":
    summary: "..."
    timestamp: "2025-10-22T15:30:00"
    ttl: 86400  # 24 часа
```

**Эффект**:
- При 10 пользователях → экономия ~90% на суммаризации
- При 100 пользователях → экономия ~99%

**Новая стоимость суммаризации**:
```
10,000 вакансий × $0.00032 × 0.10 (10% уникальных) = $0.32
```

#### 2. Пакетная обработка

**Идея**: Обрабатывать вакансии батчами, а не по одной

**Плюсы**:
- Распараллелить LLM вызовы
- Уменьшить latency

**Минусы**:
- Сложнее реализация

#### 3. Использование более дешёвой модели для первичной фильтрации

**Модель**: gpt-4o-mini (в 10 раз дешевле gemini-2.0-flash)

**Стратегия**:
```
Шаг 1: gpt-4o-mini для job_is_interesting
  - Если score < 50 → SKIP (уверенно плохо)
  - Если score > 70 → PASS (уверенно хорошо)
  - Если score 50-70 → Переход к шагу 2

Шаг 2: gemini-2.0-flash для граничных случаев
  - Более точная оценка
```

**Эффект**:
- 70% вакансий обрабатываются дешёвой моделью
- 30% вакансий требуют дорогой модели
- **Экономия**: ~40%

**Новая стоимость оценки**:
```
job_is_interesting:
  7,000 × $0.000043 (gpt-4o-mini) = $0.30
  3,000 × $0.00043 (gemini-2.0-flash) = $1.29
  Итого: $1.59 вместо $4.30
```

#### Итого с оптимизациями:

| Операция | До оптимизации | После оптимизации | Экономия |
|----------|---------------|-------------------|----------|
| Суммаризация | $3.20 | $0.32 | 90% |
| Оценка | $4.30 | $1.59 | 63% |
| Письма | $4.50 | $4.50 | 0% |
| **ИТОГО в день** | **$12.00** | **$6.41** | **47%** |

**С оптимизациями**:
- **День**: $6.41
- **Месяц**: $192.30
- **Год**: $2,339.65

- Подходит для отладки логики

- **gemini-2.0-flash** с оптимизациями

- $5,000-10,000/месяц при 100,000 откликов

**Для production (большой масштаб, > 10000 пользователей)**:
- **Hybrid подход**:
  - gemini-2.0-flash для критичных операций
  - gpt-4o-mini для массовых проверок
  - Локальные модели для простых задач
- $10,000-20,000/месяц при 500,000+ откликов

## Оптимизации для минимизации стоимости

### 1. Кэширование (Реализовано ✅)

**Что кэшировать**:
- ✅ Ответы на вопросы (`answers.yaml`)
- ⚠️ Суммаризация вакансий (TODO)
- ⚠️ Оценка пары резюме-вакансия (TODO)

**Эффект**: 30-40% экономия

---

### 2. Dual Model Strategy (Рекомендуется)

**Концепция**:
```
Дешёвая модель (gpt-4o-mini) для первичной фильтрации
  ↓ (score 50-70)
Дорогая модель (gemini-2.0-flash) для точной оценки
```

**Эффект**: 40-50% экономия на оценке

---

### 3. Batch Processing (Рекомендуется)

**Концепция**: Обрабатывать несколько вакансий одним запросом

**Пример промпта**:
```
Evaluate following 10 vacancies against the resume:

Vacancy 1: {description}
Vacancy 2: {description}
...

Output format:
1. Score: X, Reasoning: ...
2. Score: Y, Reasoning: ...
...
```

**Плюсы**:
- Меньше HTTP запросов
- Меньше overhead на токены

**Минусы**:
- Сложнее парсинг
- Риск ошибок в формате

**Эффект**: 20-30% экономия на токенах

---

### 4. Сокращение промптов (Реализовано частично)

**Идеи**:
- Удалить примеры из промптов (если качество не страдает)
- Использовать сокращённый формат резюме
- Удалить избыточные инструкции

**Эффект**: 10-15% экономия

---

### 5. Использование MONKEY_MODE для части вакансий

**Концепция**: Для очевидно подходящих вакансий пропустить LLM оценку

**Критерии "очевидно подходит"**:
- Точное совпадение job_title с резюме
- Совпадение всех keywords
- Зарплата в диапазоне

**Эффект**: 10-20% экономия

## Мониторинг и контроль расходов

### Метрики для отслеживания

**1. Стоимость на один отклик**:
```
cost_per_apply = total_llm_cost / successful_applies
```

**Целевое значение**: < $0.003

---

**2. Процент кэш-попаданий**:
```
cache_hit_rate = cached_answers / total_questions
```

**Целевое значение**: > 60% после 1000 вакансий

---

**3. Средний score вакансий**:
```
avg_score = sum(scores) / count(scores)
```

**Целевое значение**: 60-75 (хороший баланс)

---

**4. ROI оптимизаций**:
```
roi = (cost_before - cost_after) / implementation_cost
```

**Целевое значение**: > 2.0 (окупаемость за 6 месяцев)
